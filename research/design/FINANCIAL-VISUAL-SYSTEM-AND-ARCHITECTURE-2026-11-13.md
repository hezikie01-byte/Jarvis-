# J.A.R.V.I.S. — Financial Visual System & Architecture Rules

Date: 2026-11-13
Status: design/architecture proposal on research branch; not integrated into production.

## Product direction

J.A.R.V.I.S. should feel like a professional financial terminal: dark, calm, high-contrast, blue/turquoise accents, clear hierarchy, large readable figures, restrained motion. No robot mascot, face, or decorative character. The product name is text-only: J.A.R.V.I.S.

The visual system must communicate financial meaning, not merely look animated.

## Three strictly separated data layers

1. **Canonical financial facts** — user-confirmed balances, transactions, holdings, deal principals, payments and fees. These are authoritative and must never be generated by a visual simulation.
2. **Derived activity indicators** — deterministic calculations over canonical facts, with a defined period, currency, source and last-updated timestamp. They describe actual recorded activity; they are not market prices.
3. **Sandbox simulations** — hypothetical scenarios, available only inside the candlestick-indicator/simulation area. They must be visibly labeled SIMULATION, use isolated state, and never write to canonical facts or affect dashboard balances, P&L, holdings or deal records.

No component may silently mix these layers.

## Balance cards: numeric truth + background activity index

Every balance card keeps the actual balance as the dominant foreground value. A subtle background sparkline/candlestick ribbon may visualize the activity represented by that card.

The background index is an **activity index**, not a fabricated valuation:
- It is calculated from dated, confirmed ledger events relevant to the card.
- Inflows, outflows, transfers and fees remain separately classifiable; transfers between owned accounts must not be counted as income or expense.
- The aggregation window and event coverage must be available in the detail view.
- If event dates or history are missing, show a neutral/insufficient-history treatment. Never fabricate candles or interpolate unknown activity.
- If no events exist, use a quiet baseline, not a moving animation.
- The numeric balance remains readable and never changes because the background animation moves.
- Use accessible contrast and reduced-motion behavior; background motion must not distract from the amount.

### Suggested card semantics
- **Cash / available balance:** activity trace from confirmed cash movements, with inflows/outflows distinguished.
- **Invested capital / portfolio:** show value history only when genuine dated valuation snapshots exist. Otherwise show contribution/withdrawal activity, clearly labeled as activity rather than portfolio return.
- **Private deals:** show actual repayment/receipt activity and outstanding principal separately. Do not imply market liquidity or mark-to-market pricing.
- **Net worth:** show dated snapshots only. Do not infer a historical net-worth curve from current balances.

## Candlestick indicator rules

Candles are reserved for the dedicated indicator and simulation experiences, not used as decoration on every card.

For actual activity candles:
- Define a transparent activity metric and time bucket (day/week/month).
- Open/high/low/close must be mathematically derived from the chosen metric's within-period cumulative path, not invented.
- Label the metric (for example, net cash-flow activity index) and unit/base clearly.
- A positive candle does not automatically mean investment profit; it may only mean net inflow.
- Missing dates produce gaps, not fabricated flat candles.
- Keep source-event count and data coverage accessible.

For hypothetical candles:
- Put them in a sandbox with a persistent SIMULATION label.
- Show assumptions and selected date range.
- Keep simulated values in separate state/storage namespace.
- No simulated values may enter canonical balance cards, actual P&L, portfolio holdings or exports marked as actual.

## Architecture boundaries

Recommended presentation/data pipeline:

Canonical Ledger & Confirmed Deal Events
  -> Validation + reconciliation
  -> Deterministic Financial Calculation Services
  -> Read-only Activity/Valuation Series
  -> UI View Models
  -> Balance Cards / Charts / Candlesticks

Sandbox Simulation Engine
  -> isolated hypothetical inputs
  -> simulation-only series
  -> simulation workspace UI

The UI must not calculate authoritative financial results. Calculation services own money arithmetic, currency precision, event classification, period aggregation and provenance. AI may extract, summarize and explain; it must not be the authority for financial arithmetic.

Each derived series should carry:
- metricId and metricLabel
- sourceType and sourceRecordIds (or a privacy-safe evidence reference)
- currency/unit
- periodStart and periodEnd
- aggregation interval
- calculatedAt and sourceUpdatedAt
- dataCoverage / missing-period markers
- isSimulation boolean
- formulaVersion

## Visual hierarchy

1. Actual amount: largest and highest contrast.
2. Label + currency: immediately adjacent, unambiguous.
3. Activity background: low-contrast, behind or below the amount; never obscure digits.
4. Change/period context: small but readable and explicit.
5. Data freshness / incomplete history: visible, not hidden in a tooltip only.

Use color as secondary encoding, not the sole encoding: pair color with labels/icons/patterns. Avoid flashing, random motion, and animated values that suggest changing money.

## Acceptance criteria

- A user can distinguish actual balance, derived activity and hypothetical simulation at a glance.
- Changing or replaying a simulation cannot change any actual financial value.
- The same ledger snapshot and formula version produce the same activity series.
- No historical candle appears without source events or genuine valuation snapshots.
- Every card has a neutral fallback for missing history.
- Balance figures remain legible with motion disabled and on a small Android screen.
- UI tests verify that simulation state is isolated from canonical finance state.
- No production data is migrated or overwritten as part of this design work.

## Implementation sequence

1. Define the canonical event types and source-of-truth rules.
2. Build deterministic activity-series calculation with synthetic fixtures and edge-case tests.
3. Build balance-card view model and accessible dark-theme visual prototype.
4. Add candlestick simulation sandbox with strict state isolation.
5. Test Android small-screen layout, contrast, reduced motion and data gaps.
6. Only after review, plan integration into the live app; no deployment as part of this research proposal.
